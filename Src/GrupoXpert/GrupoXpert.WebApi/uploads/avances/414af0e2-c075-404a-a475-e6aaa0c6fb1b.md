# Guía de Implementación: Componente `ProgramReports`

**Versión:** 1.1  
**Fecha:** Junio 2026  
**Módulo:** GEN — Generales  
**Aplica a:** Desarrolladores que configuren pantallas con generación automática de reportes

---

## Descripción General

El componente `ProgramReports` permite la generación automática de reportes asociados a una pantalla (programa), a un bloque específico (GridView o EditForm) o a la pantalla completa. La funcionalidad se basa en el cruce entre un diccionario de valores generado en tiempo de ejecución por los componentes de la pantalla, y las tablas de configuración `PROGRAMA_REPORTES` y `PROGRAMA_REPORTES_PARAMETROS` almacenadas en base de datos Oracle.

El botón de reportes en la pantalla despliega dinámicamente un menú con los reportes disponibles según el contexto (programa / bloque), y al seleccionar uno, el sistema resuelve automáticamente los parámetros necesarios para ejecutarlo.

La arquitectura del componente separa claramente dos responsabilidades:

| Capa       | Responsabilidad |
|------------|----------------|
| **Frontend** | Construir el diccionario `Dictionary<string, string>` con el estado actual de los componentes visuales (grids, formularios) y enviarlo al backend al seleccionar un reporte. |
| **Backend**  | Consultar las tablas de configuración para resolver el mapeo entre parámetros del reporte (`nro_parametro`) e identificadores de campo (`id_programa`), extraer los valores del diccionario y ejecutar el reporte. |

---

## Backend — Estructura de Base de Datos

La configuración del componente reside en dos tablas principales del esquema, complementadas por vistas de apoyo.

```
                  +-----------------------+
                  |   PROGRAMA_REPORTES   |
                  +-----------------------+
                  | PK: programa          | <----+
                  | PK: modulo            |      |
                  | PK: reporte           |      | (Relación FK)
                  |     orden             |      |
                  |     bloque            |      |
                  +-----------------------+      |
                             |                   |
                             v 1..*              |
            +---------------------------------+  |
            |  PROGRAMA_REPORTES_PARAMETROS   |  |
            +---------------------------------+  |
            | PK, FK: programa                | -+
            | PK, FK: modulo                  |
            | PK, FK: reporte                 |
            | PK, FK: nro_parametro           |
            |         id_programa             |
            +---------------------------------+
```

### Tabla Padre: `PROGRAMA_REPORTES`

Registra la relación entre un programa (pantalla) y un reporte. Es la tabla de configuración principal.

| Columna    | Tipo           | Nulo | Descripción |
|------------|----------------|------|-------------|
| `programa` | VARCHAR2(50)   | NO   | Nombre del programa / pantalla (PK) |
| `modulo`   | NUMBER(3)      | NO   | Módulo al que pertenece el reporte (PK) |
| `reporte`  | VARCHAR2(30)   | NO   | Nombre del reporte (PK) |
| `orden`    | NUMBER(2)      | NO   | Orden de aparición del reporte en el menú |
| `bloque`   | VARCHAR2(100)  | SÍ   | Prefijo del bloque (grid o form). Si es NULL, el reporte aplica a toda la pantalla |

**Clave primaria:** `(programa, modulo, reporte)`  
**Clave foránea:** `(modulo, reporte)` → `reportes(modulo, reporte)`

### Tabla Hija: `PROGRAMA_REPORTES_PARAMETROS`

Registra el mapeo entre cada parámetro del reporte y el campo (`id_programa`) del componente de pantalla que provee su valor.

| Columna         | Tipo           | Nulo | Descripción |
|-----------------|----------------|------|-------------|
| `programa`      | VARCHAR2(50)   | NO   | Nombre del programa (PK) |
| `modulo`        | NUMBER(3)      | NO   | Módulo del reporte (PK) |
| `reporte`       | VARCHAR2(30)   | NO   | Nombre del reporte (PK) |
| `nro_parametro` | NUMBER(2)      | NO   | Número de orden del parámetro en el reporte |
| `id_programa`   | VARCHAR2(200)  | NO   | Identificador del campo en pantalla que entrega el valor |

**Clave primaria:** `(programa, modulo, reporte, nro_parametro)`  
**Claves foráneas:**
- `(modulo, reporte, nro_parametro)` → `reportes_parametros(modulo, reporte, nro_parametro)`
- `(programa, modulo, reporte)` → `programa_reportes(programa, modulo, reporte)`

### Vistas de Apoyo

| Vista                              | Descripción |
|------------------------------------|-------------|
| `V_PROGRAMA_REPORTES`              | Extiende `PROGRAMA_REPORTES` con título, descripción y submódulo del reporte desde `V_REPORTES` |
| `V_PROGRAMA_REPORTES_PARAMETROS`   | Extiende `PROGRAMA_REPORTES_PARAMETROS` con información del parámetro (`tipo_variable`, `obligatorio`, `valor_defecto`) desde `REPORTES_PARAMETROS` |

## Frontend — Generación del Diccionario de Pantalla

Cada pantalla que usa el componente `ProgramReports` genera en tiempo de ejecución un `Dictionary<string, string>`, donde:

- **Key:** `id_programa` — identificador único del campo dentro del componente de pantalla.
- **Value:** valor actual del campo en el momento de solicitar el reporte.

### Regla de Construcción del `id_programa`

```
id_programa = {PrefijoDelComponente}_{PropiedadDelModelo}
```

### Ejemplo con GridView

Si la grid tiene el prefijo `DgvUsuBot` y el modelo expone la propiedad `User`, el id resultante es:

```
DgvUsuBot_User
```

El diccionario de esa pantalla tendría entradas como:

| Key (id_programa)       | Value (en pantalla)     |
|-------------------------|-------------------------|
| `DgvUsuBot_User`        | `GALVAREZ`              |
| `DgvUsuBot_Order`       | `1`                     |
| `DgvUsuBot_Date`        | `27/04/2026 15.11`      |

### Pantallas con Múltiples Bloques

Para pantallas con múltiples grids o formularios, cada bloque genera su propio conjunto de entradas con su prefijo correspondiente:

| Bloque  | Key (id_programa)              | Value                    |
|---------|--------------------------------|--------------------------|
| Grid1   | `DgvUsuBot_User`               | `GALVAREZ`               |
|         | `DgvUsuBot_Order`              | `1`                      |
|         | `DgvUsuBot_Date`               | `27/04/2026 15.11`       |
| Grid2   | `DgvUsuBot_2_Bloque_User`      | `GALVAREZ`               |
|         | `DgvUsuBot_2_Bloque_Program`   | `GEN_CORREOS_555`        |
| Grid3   | `DgvUsuBot_3_Bloque_User`      | `GALVAREZ`               |
|         | `DgvUsuBot_3_Bloque_Program`   | `GEN_CORREOS`            |
|         | `DgvUsuBot_3_Bloque_Date`      | `27/04/2026 15.11`       |

## Backend — Flujo de Ejecución

Cuando el usuario selecciona un reporte, el backend ejecuta el siguiente proceso:

```
[Usuario hace clic en Reporte]
       │
       ▼
[Frontend genera Dictionary<string, string>]
       │  Representa el estado actual de grids/formularios
       │  (Clave: id_programa, Valor: dato)
       │
       ▼
[Backend consulta V_PROGRAMA_REPORTES]
       │  Filtra por programa y bloque activo
       │  Construye el menú de reportes (ordenado por "orden")
       │
       ▼
[Usuario selecciona un reporte]
       │
       ▼
[Backend consulta V_PROGRAMA_REPORTES_PARAMETROS]
       │  Obtiene el mapeo [nro_parametro ↔ id_programa] para el reporte
       │
       ▼
[Resolución de Parámetros]
       │  Por cada nro_parametro, busca el id_programa en el diccionario
       │  y extrae el valor actual del campo
       │
       ▼
[Ejecución del Reporte]
       │  Envía al motor de reportes los parámetros resueltos con sus valores reales
```

### Detalle de la Resolución de Parámetros

1. El componente consulta `V_PROGRAMA_REPORTES` filtrando por `programa` y `bloque` activo.
2. Se construye el menú dinámico de reportes disponibles (ordenado por campo `orden`).
3. El usuario selecciona un reporte del menú.
4. El componente consulta `V_PROGRAMA_REPORTES_PARAMETROS` para el reporte seleccionado.
5. Por cada fila retornada, busca el `id_programa` en el diccionario de la pantalla.
6. Obtiene el valor actual del campo y lo asigna al `nro_parametro` correspondiente.
7. Ejecuta el reporte enviando los parámetros resueltos.

## Paso a Paso: Configuración de un Nuevo Reporte en una Pantalla

### Paso 1 — Identificar el nombre del programa

El nombre del programa es el identificador de la pantalla en el sistema, por ejemplo: `MVC_USUARIOS_BOT`.

### Paso 2 — Identificar el bloque (si aplica)

Si el reporte debe aparecer sólo cuando el usuario está interactuando con una grid o formulario específico, se registra el prefijo de ese componente en el campo `bloque`. Si aplica para toda la pantalla, se deja `NULL`.

**Ejemplos de bloque:**
- `DgvUsuBot` → Grid principal de la pantalla
- `DgvUsuBot_2_Bloque` → Segunda grid o sección
- `Grid1`, `Grid2` → Nomenclatura alternativa
- `NULL` → El reporte aparece siempre, independiente del bloque activo

### Paso 3 — Insertar en `PROGRAMA_REPORTES`

```sql
INSERT INTO programa_reportes (programa, modulo, reporte, orden, bloque)
VALUES ('MVC_USUARIOS_BOT', 10, 'R_TABGEN', 1, NULL);

-- Reporte asociado a un bloque específico:
INSERT INTO programa_reportes (programa, modulo, reporte, orden, bloque)
VALUES ('MVC_USUARIOS_BOT', 10, 'R_TABGEN_DETALLE', 1, 'DgvUsuBot_3_Bloque');

COMMIT;
```

> **Nota:** El campo `reporte` debe existir previamente en la tabla `REPORTES` con el mismo `modulo`.

### Paso 4 — Identificar los parámetros del reporte

Consultar los parámetros definidos para el reporte en la tabla `REPORTES_PARAMETROS`:

```sql
SELECT nro_parametro, parametro, d_parametro, tipo_variable, obligatorio
FROM reportes_parametros
WHERE modulo = 10
  AND reporte = 'R_TABGEN_DETALLE'
ORDER BY nro_parametro;
```

### Paso 5 — Identificar los `id_programa` disponibles en pantalla

Revisar el diccionario generado por la pantalla. Los `id_programa` disponibles siguen la convención:

```
{Prefijo del componente}_{NombrePropiedad}
```

Consultar o solicitar al desarrollador de la pantalla la lista de claves disponibles en el diccionario.

### Paso 6 — Insertar en `PROGRAMA_REPORTES_PARAMETROS`

Mapear cada `nro_parametro` del reporte con el `id_programa` del campo que provee ese valor:

```sql
-- Parámetro 1 del reporte → campo User de la grid
INSERT INTO programa_reportes_parametros (programa, modulo, reporte, nro_parametro, id_programa)
VALUES ('MVC_USUARIOS_BOT', 10, 'R_TABGEN_DETALLE', 1, 'DgvUsuBot_3_Bloque_User');

-- Parámetro 2 del reporte → campo Program de la grid
INSERT INTO programa_reportes_parametros (programa, modulo, reporte, nro_parametro, id_programa)
VALUES ('MVC_USUARIOS_BOT', 10, 'R_TABGEN_DETALLE', 2, 'DgvUsuBot_3_Bloque_Program');

-- Parámetro 3 del reporte → campo Date de la grid
INSERT INTO programa_reportes_parametros (programa, modulo, reporte, nro_parametro, id_programa)
VALUES ('MVC_USUARIOS_BOT', 10, 'R_TABGEN_DETALLE', 3, 'DgvUsuBot_3_Bloque_Date');

COMMIT;
```

### Paso 7 — Verificar la configuración

Usar las vistas extendidas para validar que el mapeo es correcto antes de probar en pantalla:

```sql
-- Verificar reportes configurados para el programa
SELECT programa, modulo, reporte, titulo, orden, bloque
FROM v_programa_reportes
WHERE programa = 'MVC_USUARIOS_BOT'
ORDER BY bloque, orden;

-- Verificar parámetros mapeados
SELECT programa, reporte, nro_parametro, id_programa, parametro, d_parametro, tipo_variable, obligatorio
FROM v_programa_reportes_parametros
WHERE programa = 'MVC_USUARIOS_BOT'
  AND reporte = 'R_TABGEN_DETALLE'
ORDER BY nro_parametro;
```

## Ejemplo Completo

**Escenario:** La pantalla `MVC_USUARIOS_BOT` tiene una grid con prefijo `DgvUsuBot_3_Bloque`. Se quiere configurar el reporte `R_TABGEN` (módulo 10) que requiere tres parámetros: usuario, programa y fecha.

### 1. Insertar en `PROGRAMA_REPORTES` (Backend — Configuración):

```sql
INSERT INTO programa_reportes (programa, modulo, reporte, orden, bloque)
VALUES ('MVC_USUARIOS_BOT', 10, 'R_TABGEN', 1, 'DgvUsuBot_3_Bloque');
COMMIT;
```

### 2. Insertar en `PROGRAMA_REPORTES_PARAMETROS` (Backend — Configuración):

```sql
INSERT INTO programa_reportes_parametros VALUES ('MVC_USUARIOS_BOT', 10, 'R_TABGEN', 1, 'DgvUsuBot_3_Bloque_User');
INSERT INTO programa_reportes_parametros VALUES ('MVC_USUARIOS_BOT', 10, 'R_TABGEN', 2, 'DgvUsuBot_3_Bloque_Program');
INSERT INTO programa_reportes_parametros VALUES ('MVC_USUARIOS_BOT', 10, 'R_TABGEN', 3, 'DgvUsuBot_3_Bloque_Date');
COMMIT;
```

### 3. Diccionario generado por el Frontend en tiempo de ejecución:

```csharp
var screenData = new Dictionary<string, string> {
    { "DgvUsuBot_3_Bloque_User",    "GALVAREZ"           },
    { "DgvUsuBot_3_Bloque_Program", "GEN_CORREOS"        },
    { "DgvUsuBot_3_Bloque_Date",    "27/04/2026 15:11"   }
};
```

### 4. Resultado de la resolución (Backend):

Cuando el usuario seleccione el reporte `R_TABGEN` desde el bloque `DgvUsuBot_3_Bloque`, el sistema construirá automáticamente los parámetros así:

| Parámetro | `id_programa`                  | Valor resuelto del diccionario |
|-----------|--------------------------------|-------------------------------|
| 1         | `DgvUsuBot_3_Bloque_User`      | `GALVAREZ`                    |
| 2         | `DgvUsuBot_3_Bloque_Program`   | `GEN_CORREOS`                 |
| 3         | `DgvUsuBot_3_Bloque_Date`      | `27/04/2026 15.11`            |

## Consideraciones y Buenas Prácticas

- **El campo `bloque` es sensible al prefijo exacto.** Debe coincidir con el prefijo del componente de pantalla tal como lo genera el diccionario; cualquier diferencia de mayúsculas o caracteres impedirá la resolución del reporte.
- **Si `bloque` es NULL en `PROGRAMA_REPORTES`**, el reporte aparecerá en el menú sin importar qué bloque esté activo en la pantalla.
- **El `id_programa` en `PROGRAMA_REPORTES_PARAMETROS` debe existir como clave en el diccionario** generado por la pantalla en tiempo de ejecución. Si la clave no se encuentra, el parámetro quedará sin valor; verificar el campo `obligatorio` en `REPORTES_PARAMETROS` para saber si esto genera un error de validación.
- **El `nro_parametro` debe corresponder exactamente** al número de parámetro definido en `REPORTES_PARAMETROS`; no es un orden libre sino una referencia de FK.
- **Antes de insertar**, confirmar que el reporte existe en la tabla `REPORTES` con el módulo correcto, ya que existe FK hacia esa tabla.
- **Permisos:** El rol `r_gen_consulta` tiene `SELECT` sobre las tablas y vistas. Los inserts de configuración deben realizarse con el usuario propietario del esquema o un rol con privilegios de escritura.
- **Un mismo reporte puede estar asociado a múltiples programas**, siempre que se inserte una fila por cada combinación `(programa, modulo, reporte)` en ambas tablas.
- **La nomenclatura de `id_programa` debe ser consistente** entre el frontend y el backend. Cualquier discrepancia en el nombre de la clave impedirá la resolución del parámetro correspondiente.

## Referencia de Objetos de Base de Datos

| Objeto                              | Tipo    | Descripción |
|-------------------------------------|---------|-------------|
| `PROGRAMA_REPORTES`                 | Tabla   | Relación programa ↔ reporte |
| `PROGRAMA_REPORTES_PARAMETROS`      | Tabla   | Mapeo campo de pantalla ↔ parámetro del reporte |
| `V_PROGRAMA_REPORTES`               | Vista   | Extiende la tabla padre con datos del reporte |
| `V_PROGRAMA_REPORTES_PARAMETROS`    | Vista   | Extiende la tabla hija con metadatos del parámetro |
| `REPORTES`                          | Tabla   | Catálogo maestro de reportes (preexistente) |
| `REPORTES_PARAMETROS`               | Tabla   | Parámetros definidos por reporte (preexistente) |
